## 1. 意图与动机

用户经常用 Xnip、macOS 系统截图或微信截图截一张（或几张）图，想马上发到局域网里的另一台机器上，通常还想配一句说明。现在的问题是：

- 焦点在输入框里时按 ⌘V / Ctrl+V，图片**什么都不会发生**（`MainPage.tsx` 的全局 paste 处理器会主动跳过可编辑元素）。
- 焦点不在输入框里时，粘贴图片会**立刻上传**，没有机会确认或删掉，也不能配文字。
- 文字和图片只能各自成为一条消息，接收方看到的上下文是分散的。
- 点图片会跳到新标签页，看图不方便。

目标体验：像在聊天软件里一样，把截图粘贴进输入框，攒几张、配一句话、删掉贴错的那张，一次发出；对方看到的是**一张卡片**。

## 2. 目标 / 非目标 / 反目标

### 2.1 目标

1. **[用户定]** 在任意已连入 LanDrop 的设备（Host 或 Peer 浏览器）上，焦点在输入框中按 ⌘V（mac）/ Ctrl+V（Windows/Linux）可粘贴剪贴板中的图片。
2. **[用户定]** 粘贴的图片先进入**待发送区**，发送前每个附件都可以单独删除（✕）。
3. **[用户定]** 支持多张图片，连续粘贴会累加。
4. **[用户定]** 📎 选择文件、往页面上拖文件、粘贴截图，三种方式都进入**同一个**待发送区，和输入框文字一起作为**一条消息**发送。附件可以是任意文件，不限于图片。
5. **[用户定]** 文字 + N 个附件发送后，所有设备上显示为**一条消息（一张卡片）**。
6. **[用户定]** 消息中每张图片（以及每个文件）都可以**单独下载**。
7. **[用户定]** 分享链接以**整条消息**为单位，不拆分成单张图片分享。
8. **[用户定]** 点击消息里的图片，在页面内**弹出图片查看层**。
9. **[用户定]** 待发送区放在输入框**文字上方**（效果图方案 A）。

### 2.2 非目标

- 编辑已发送的消息、对图片做标注或裁剪。
- 图片压缩或转码：原样发送原始字节。
- 改变 CLI `landrop send` 的行为：它仍然产生现有的单文本 / 单文件条目。
- 对已有的 `text` / `file` 条目做数据迁移（Store 是内存的，重启即清空，无需迁移）。

### 2.3 反目标（即使"能用"也算失败）[我的判断]

- **出现半条消息**：接收方先看到文字、图片再陆续出现，或者上传中途失败，留下一条缺图的消息。消息必须在所有附件都传完后才**整条**出现。
- **发送失败后内容丢失**：上传失败或网络断开时，待发送区里的附件和文字被清空，用户只能重新截图。
- 在输入框里粘贴**纯文字**的行为发生变化（必须仍是浏览器默认的插入文字）。
- 粘贴大图时页面卡顿：待发送区缩略图应使用 `URL.createObjectURL`，不能把整张图读成 base64 放进 DOM；删除或发送后要 `revokeObjectURL`。

## 3. 交互设计

### 3.1 待发送区（Composer）

布局 **[用户定]** 方案 A：

```
┌──────────────────────────────────────┐
│ [img✕] [img✕] [report.pdf 2.3MB ✕]   │ ← 待发送区，没有附件时不占空间
│ 看下这两张截图，还有报告                 │ ← textarea
│ 📎 选择文件                 发送 ⌘↵   │
└──────────────────────────────────────┘
```

- 图片附件显示为约 64×64 的缩略图（`object-fit: cover`），右上角有 ✕；非图片附件显示为小卡片（文件名 + 大小 + ✕）。是否算"图片"沿用现有的 `isImageMime`。
- 附件太多时待发送区换行，最多占几行后改为内部滚动 [留给实现方]。
- **发送按钮可用条件**：文字非空白，**或**至少有一个附件。⌘↵ / Ctrl+↵ 同样适用。
- 超过 `max_size` 的文件在**加入待发送区时**就标红，并提示"文件过大"；发送按钮在仍有超限附件时不可用 [我的判断]。超限附件可以用 ✕ 删掉。
- 每条消息最多 **20 个附件**；超出的部分不加入，并提示"最多 20 个附件" [我的判断]。
- 现有的"文字超过 1 MiB → 作为文件发送"：改为把文字转成 `text.txt` **加入待发送区**并清空输入框，而不是直接上传 [我的判断]。

### 3.2 附件的三个入口

| 入口 | 现在 | 改后 |
|---|---|---|
| 焦点在输入框中粘贴 | 图片无反应，文字插入 | 剪贴板里**有文件**时 → 全部加入待发送区并 `preventDefault`；**没有文件**时 → 保持浏览器默认（插入文字） **[用户定]** |
| 焦点不在输入框时粘贴 | 文件立刻上传；文字立刻发送 | 文件 → 加入待发送区并让输入框获得焦点；文字 → 输入框和待发送区**都为空**时保持现状（立刻发送），否则把文字**追加到输入框**并聚焦，避免它抢在草稿前面单独发出 [我的判断] |
| 📎 选择文件 | 立刻上传 | 加入待发送区 **[用户定]** |
| 拖拽到页面 | 立刻上传 | 加入待发送区 **[用户定]** |

- 剪贴板同时有图片和文字时（例如从网页复制图片，会同时带 `text/html` 或 `text/plain`）：**只取文件**，忽略文字 [我的判断]。
- 截图粘贴出来的文件名通常是 `image.png`，多张会重名。加入待发送区时重命名为 `截图-YYYYMMDD-HHMMSS[-n].<ext>` 风格（英文界面用 `screenshot-…`），扩展名取自 MIME [我的判断]；用户选的、拖进来的文件保持原名。
- **发送中**再粘贴、拖入或选择文件：不加入、不排队，提示"正在发送，请稍候" [我的判断]；保持单一草稿的状态模型。
- 文件夹 / 目录面板（`--dir` 的 Folder 标签页）打开时，粘贴和拖拽的行为不变（与现有逻辑一致：有弹层时不处理）。

### 3.3 发送过程

- 按发送后，待发送区和文字进入"发送中"状态：附件上显示上传进度（总进度或每个附件各自的进度 [留给实现方]），✕ 和发送按钮不可用，可以**取消**。
- **全部附件上传成功并创建消息后**，才清空输入框和待发送区，并释放 object URL。
- **任何附件上传失败**：整条消息不创建；待发送区和文字原样保留，失败的附件标红并显示原因（沿用 `errText` 的错误码文案），用户可以删掉它后重新发送，或者直接重试。
- 发送中用户关闭页面或断网：服务端不会产生消息（见 §4.2 的暂存与清理）。
- **发送类型按草稿内容决定 [用户定]**：
  | 草稿内容 | 产生的条目 |
  |---|---|
  | 只有文字 | 现有 `text` 条目（`POST /api/text`，行为不变） |
  | 恰好 1 个附件、没有文字 | 现有 `file` 条目（与现在单文件上传完全相同：分享、自动保存、CLI 均不变） |
  | 其他（文字 + ≥1 附件，或 ≥2 附件） | 新的 `message` 条目 |
  单附件的情况可以直接走现有 `/api/upload`；它在 UI 上和图文消息里的图片一样，可以点开查看层。

### 3.4 消息卡片（Feed）

```
MacBook-Pro · 刚刚
看下这两张截图，还有报告          ← 文字（沿用 TextBody 的折叠、代码高亮等）
┌────┐┌────┐┌────┐
│ ⬇  ││ ⬇  ││ ⬇  │              ← 图片网格，每格右下角有单独下载按钮
└────┘└────┘└────┘
📄 report.pdf  2.3 MB  ⬇ 下载     ← 非图片附件，一个附件一行
[复制文字] [分享] [🗑]            ← 整条消息的操作
```

- 图片网格：1 张时显示较大的单图（保持比例，限制最大高度）；2 张及以上用方格网格，每行最多 3 张 [我的判断，具体尺寸留给实现方]。
- 图片按发送时在待发送区里的顺序显示；非图片附件排在图片后面 [我的判断]。
- "复制文字"只在有文字时显示。
- **删除**和**过期**以整条消息为单位：删除消息会删掉它的所有附件文件。
- Host 开启自动保存（`OnFileStored`）时，消息里的**每个附件**都按现有规则落盘；文字部分不落盘（现有文本条目本来就不自动保存）[我的判断]。

### 3.5 图片查看层

- 点击消息里的任意图片，打开页面内的全屏查看层：深色半透明背景，图片居中并适配屏幕（`object-fit: contain`）。
- 同一条消息中有多张图片时：左右箭头按钮、键盘 ← → 键、触屏左右滑动都可以切换；底部显示 `2 / 3`。
- 右上角有**下载**和**关闭**按钮；Esc 或点击背景也可以关闭。
- 查看层要计入现有的 `openOverlay` 计数（打开时全局粘贴不处理），并遵循现有 `Dialog` 的焦点管理和可访问性做法。
- **单图片 `file` 条目**（包括"1 个附件、没有文字"发出去的截图）也改为点击打开查看层（只有 1 张），不再跳到新标签页 [我的判断]。

### 3.6 分享落地页

- 分享单位是整条消息 **[用户定]**。落地页显示：过期时间、文字（带复制按钮）、图片网格（每张可以单独下载，可以打开查看层）、非图片附件列表（每个可以单独下载）。
- **只限有效期，不限次数 [用户定]**：`message` 类型的分享链接只有有效期（沿用现有 60 秒～24 小时的范围），在有效期内可以任意打开、任意下载其中的附件。因此不需要"查看内容"按钮，也不需要临时凭据；落地页加载后直接显示内容。
- 分享弹窗（`ShareDialog`）对 `message` 类型**隐藏**"下载次数"选项，只保留有效期。
- 现有 `text` / `file` 条目的分享（含次数限制）**本次不改动 [用户定]**；是否全局取消次数限制以后另议。

## 4. 数据与接口

### 4.1 数据模型

在 `store.Kind` 新增 `message` 类型 [我的判断，名称留给实现方]：

```go
type Attachment struct {
    ID   string `json:"id"`   // 在消息内唯一；文件在磁盘上的路径由 store 管理
    Name string `json:"name"`
    Size int64  `json:"size"`
    MIME string `json:"mime"`
}

// Item 新增字段
Attachments []Attachment `json:"attachments,omitempty"`
// message 类型：Content 为可选文字（可以为空），Attachments 至少 1 个
```

- 现有的 `text` 和 `file` 类型保持不变（CLI、`/api/local/*`、旧前端代码路径继续使用）。
- 文字长度限制沿用 `MaxText`（1 MiB）；每个附件大小限制沿用 `MaxSize`；附件数量上限 20。
- 前端 `api.ts` 的 `Item` 类型同步更新；`Feed` / `ItemCard` 根据 `type` 渲染。

### 4.2 上传流程（保证"整条出现"）

要求：消息只在所有附件都写入磁盘后，才作为**一个** `item.created` 事件发布。

建议方案 [留给实现方，可以换成等价方案]：

1. `POST /api/attachments`：上传单个文件（流式写盘，复用现有 `AddFile` 的大小、磁盘空间检查和 `.part` 逻辑），写入**暂存区**，返回暂存 ID。**不**发布事件、**不**出现在列表中。
2. `POST /api/messages {content, attachments:[暂存ID…]}`：校验所有暂存 ID 都属于当前会话（peer）且仍然存在，然后原子地创建 `message` 条目、把暂存文件转为正式附件，最后发布 `item.created`。
3. 暂存文件在一段时间（例如 30 分钟）内没有被消息引用就清理掉（可以复用现有的 `Sweep` 周期）。进程退出时按现有 `Store.Close` 规则一起处理。

客户端在发送时并发上传附件（复用 `lib/uploads.ts` 的并发和测速逻辑），全部成功后再调用第 2 步。这样也天然支持"单个附件失败后只重试这一个"。

同样遵循现有的 `origin` + `session` 中间件、`Content-Length` 预检、`disk_full` / `too_large` 错误码。

### 4.3 下载与内联

- `GET /api/items/{id}/attachments/{aid}/raw[?inline=1]`：下载或内联单个附件。内联只对现有的 `inlineMIMEs` 白名单生效（png/jpeg/gif/webp），其余类型强制作为附件下载，与现有安全策略一致。
- 是否提供"整条消息打包下载"：**不提供** [我的判断，用户只要求单张下载]。

### 4.4 分享接口

- `POST /api/items/{id}/share` 对 `message` 类型同样可用。
- `Share.Create` 对 `message` 不设次数（例如 `Remaining` 不参与判断，或用一个表示"无限"的值）[留给实现方]；`Peek` 只检查过期。
- `GET /api/s/{id}` 对 `message` 返回 `type: "message"`、文字和附件列表（名称、大小、MIME、附件 ID）、过期时间。
- `GET /s/{id}/attachments/{aid}/raw[?inline=1]`：在链接有效期内下载或内联单个附件，不消耗任何次数。内联同样只对 `inlineMIMEs` 白名单生效，以便落地页显示图片缩略图和查看层；其余一律按 `attachment` 下载。

### 4.5 事件与同步

- 沿用现有 SSE：`item.created` / `item.deleted`，携带完整 `message` 条目。`since` 补齐逻辑不变。
- 暂存附件**不**产生任何事件。

## 6. 测试要点

- **Go**：store 新类型的创建、删除、Sweep（附件文件随消息一起删除）；暂存过期清理；消息创建时校验暂存 ID 归属（A 设备不能引用 B 设备的暂存文件）；附件数量、大小、磁盘满的校验；附件 raw 下载的内联白名单；`message` 分享链接在有效期内可以重复下载、过期后返回 410；`text`/`file` 分享的次数行为不变（回归测试）。
- **前端单测**：粘贴事件分流（有文件 / 只有文字 / 输入框内外）；截图重命名；发送按钮可用条件；失败时保留待发送区。
- **Playwright e2e**：在输入框中粘贴两张图片 + 文字 → 删掉一张 → 发送 → 另一个浏览器上下文中出现**一条**卡片，包含 1 张图和文字；点击图片打开查看层，按 Esc 关闭；单张下载可用。
